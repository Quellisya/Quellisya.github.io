一分钟速览

  • 难度：入门（在 ret2text 之后、ROP 之前；正好理解“程序自己开了个 RWX 页”是什么体验）
  • 考点：ret2shellcode、mmap 的 prot / flags、RWX 页、shellcode 生成、栈偏移、两次 read 的时序同步
  • 保护：Full RELRO、No Canary、NX enabled、PIE enabled、not stripped
  • 漏洞：read(0, v4, 0x100)，v4 只有 40 字节
  • 两段输入：第一次 read 把 shellcode 写进 mmap 出来的 0x233000；第二次 read 溢出 v4，覆盖返回地址
  • 偏移：0x30 + 0x8 = 0x38（不是 0x28 + 8，因为 v4 和 rbp 之间还夹着一个 buf 指针）
  • 关键地址：buf = 0x233000（mmap 的 hint，运行时验证）
  • 利用链：shellcode → 0x233000 → 覆盖返回地址为 0x233000 → main 的 ret 跳过去执行
  • 结果：execve("/bin/sh") 拿到 shell，cat /flag
  • flag：CTF2{56bf4633-e6ef-43a5-b0ef-eb4cba7d6e50}
  • 思考题：文中有 9 道，答案默认折叠，建议先自己想一遍

阅读说明

  • 前置知识：栈溢出、返回地址、read / puts、pwntools 基本用法、checksec。如果还没做过 32 位 ret2text，建议先看 not_the_same。
  • 工具：file、checksec、IDA、gdb + pwndbg、pwntools
  • 环境：Linux（Kali / Ubuntu）。文中的靶场地址是当时的临时环境，现在多半已经失效，请换成自己的靶场或本地环境
  • 本文所有操作仅用于授权靶场和本地环境，请勿对未授权的目标做任何测试

做题路线

file / checksec → IDA 看 main → 读懂 mmap 的六个参数 → 发现两次 read → 算偏移 → 生成 shellcode → 确认 0x233000 可执行 → 写 exp → 同步两次 send → 拿 flag

先把程序看明白

这道题和前面几道不太一样：前面是“程序里有后门”或者“程序里有 system”，这题是程序亲手给你开了一块可写可执行的内存，然后等你把代码塞进去。

如果只看这张表，很容易得出一个结论：

PIE 开了，NX 也开了，是不是只能去泄漏地址、打 ROP 了？

先别急。checksec 看的是程序被加载时的默认保护，它管不到程序自己后面做了什么。这道题的 main 里就有一行 mmap，亲自把一块内存设成了 RWX。

你可能会说：这算什么保护绕过？

严格来说，这不算“绕过”，这是程序自己把门打开了。我们要做的，只是找到这扇门，然后把 shellcode 送进去。

思考 01｜checksec 显示 NX enabled、PIE enabled，为什么这题还能执行 shellcode？

因为 NX 和 PIE 管的是不同的东西，而且都不是“全局禁止执行任意代码”。

  • NX 是页表里的一个权限位。它默认让栈、堆这些区域不可执行，但 mmap 的 prot 参数可以显式带上 PROT_EXEC。这题 prot = 7，也就是 RWX，这一页就是可执行的。NX 拦的是“栈上的代码”，不是“所有不是代码段的代码”。
  • PIE 随机化的是 ELF 映像本身的加载基址。0x233000 不是程序里的地址，而是程序调用 mmap 时请求出来的一块匿名内存。它不跟着 PIE 的基址走。

所以 PIE 和 NX 都还在，但它们的管辖范围刚好都不包括这块 mmap 页。checksec 没有骗你，只是它描述的是默认状态，不是程序运行时的全部状态。

用 IDA 打开，F5：

init 一般是 setvbuf 之类的缓冲区初始化，和利用本身没关系，这里不展开。真正重要的是下面三件事：mmap 开了什么页、第一次 read 写什么、第二次 read 为什么能溢出。

第一行：mmap

mmap 的六个参数，正好对应 64 位调用约定的六个寄存器：

参数 值 含义
addr 0x233000 想要的起始地址（注意：只是 hint，后面细说）
length 0x1000 4 KB，正好一页
prot 7 PROT_READ + PROT_WRITE + PROT_EXEC，也就是 RWX
flags 34（0x22） MAP_PRIVATE + MAP_ANONYMOUS
fd -1 匿名映射，没有文件
offset 0 从文件偏移 0 开始（匿名映射用不上）

重点看 prot = 7。

7 的二进制是 111，三位分别对应：

也就是说，这块 4 KB 的内存既能读、又能写、还能执行。

这就解释了为什么 NX 开着也没关系：NX 是“默认不给执行”，不是“禁止申请执行权限”。程序自己用 mmap 申请了 PROT_EXEC，内核就给它一页可执行内存。

所以记住一句话：ret2shellcode 的第一个前提，就是必须有一段可以运行的内存。 这题的程序自己把前提准备好了。

再看 flags = 34 = 0x22：

  • MAP_PRIVATE：私有映射，写时复制，不共享；
  • MAP_ANONYMOUS：匿名映射，不关联任何文件，内容初始化为 0，所以 fd 必须是 -1。

这里没有 MAP_FIXED（0x10）。这一点很关键。

思考 02｜mmap 没有 MAP_FIXED，为什么 0x233000 还能稳定拿到？

mmap 的 addr 参数在没有 MAP_FIXED 时只是建议地址：内核会尽量按这个地址分配，但不保证。

这题能稳定拿到，靠的是三个条件：

  1. 页对齐：0x233000 是 0x1000 的整数倍（0x233000 = 0x233 × 0x1000）；
  2. 这段地址是空的：正常 PIE 程序的代码、栈、libc 都不会落在这么低的匿名区；
  3. 高于 mmap_min_addr：这个值通常是 65536，0x233000 远高于它，不会被安全策略拒绝。

内核发现“你想要 0x233000，这块正好空着”，就直接给了。

但这不是语言层面的保证。如果程序在它之前映射了别的东西，或者内核决定换个地址，buf 就不是 0x233000，payload 里的返回地址也就错了。所以做题时最好在 gdb 里 vmmap 确认一次。

如果加了 MAP_FIXED，内核会强制使用这个地址，并覆盖掉该范围内已有的映射，更危险。出题人没用它，说明他相信这块地址是空的。

两次 read：两段输入

第一次 read 的目标是 buf，也就是 mmap 返回的那个指针，指向 0x233000。长度 0x100，也就是 256 字节。

第二次 read 的目标是 v4，一个只有 40 字节的栈数组，长度还是 0x100。

所以：

  • 第一次 read 是**“存储器”**：我们把 shellcode 放进去；
  • 第二次 read 是**“控制器”**：我们用它溢出 v4，覆盖 main 的返回地址。

两段输入，各司其职。

看反汇编确认参数

图 3：六个 mov 对应 mmap 的六个参数，随后是两次 read

后面两次 read 的取地址方式很值得对比：

第一次是 mov rax, [rbp-8]，第二次是 lea rax, [rbp-0x30]。这不是编译器随便写的，而是 C 语言里**“指针变量”和“数组”**的区别在汇编里的样子。

思考 03｜第一次 read 用 mov rax, [rbp-8]，第二次用 lea rax, [rbp-0x30]，这个区别说明了什么？

buf 是一个指针变量，它本身存在 rbp-8，里面装的是 mmap 返回的地址。所以要先 mov rax, [rbp-8]，把指针的值取出来，才是要写的目标地址。

v4 是一个数组，数组名在表达式里会退化成首元素地址。编译器不需要先存一个指针，直接 lea rax, [rbp-0x30] 算出它的地址就行。

这也顺便告诉我们两件事：

  • buf 指向的是别处（0x233000 那一页），不是栈；
  • v4 就在栈上，范围是 rbp-0x30 到 rbp。

后面算偏移时，这个布局就是关键。

思考 04｜v4 明明只有 40 字节，为什么偏移是 0x30 + 8，而不是 0x28 + 8？

因为 0x28 只是 v4 自己占的范围：rbp-0x30 到 rbp-0x8。

紧接着 rbp-0x8 到 rbp 这 8 个字节，是 buf 指针。编译器为了布局方便，把 buf 塞在了 v4 和保存的 rbp 之间。

思考 05｜把 buf 指针覆盖成 'A' * 8，程序不会崩吗？

不会，因为 buf 在被覆盖之后已经不再被使用了。

程序对 buf 的使用只有两次：

  1. mmap 的返回值存进 buf；
  2. 第一次 read(0, buf, 0x100) 把 buf 当目标地址。

第二次 read 之后，程序只执行 puts("Ok.See you!") 和 return 0，再也没碰过 buf。所以把 [rbp-8] 写成 0x4141414141414141 没有影响。

这也是 pwn 里常见的一个判断：溢出会覆盖很多变量，但只有“溢出之后还会被使用”的变量才需要小心。 这题 buf 不在这个名单里，所以可以放心用 'A' 填过去。

shellcode 到底是什么

现在方向已经很清楚了：

  1. 第一次 read 把一段代码写进 0x233000；
  2. 第二次 read 覆盖返回地址，让 main 的 ret 跳到 0x233000。

剩下的问题只有一个：写进去的这段代码是什么？

答案是 shellcode。

一句话定义

shellcode 是一段位置无关的机器码，被程序执行之后，通常会给攻击者一个 shell。最经典的行为就是：

名字叫 shellcode，但它不一定只能拿 shell。任何“执行后能达到目的”的机器码都算，比如：

  • execve("/bin/sh", ...)：拿交互式 shell；
  • execve("/bin/cat", ["cat", "/flag"], ...)：直接读 flag；
  • 反向连接、下载执行、exit(0) 等等。

这题用最经典的 execve("/bin/sh")。

为什么它在这题特别合适

前面几道题我们都在想办法调用程序里已有的函数：后门、system@plt、libc 里的 system。

shellcode 不一样，它不依赖程序里的任何符号：

  • 不需要知道 system 在哪；
  • 不需要知道 libc 版本；
  • 不需要 GOT / PLT；
  • 不需要 PIE 基址。

它只做一件事：把参数放进寄存器，然后 syscall。内核负责执行 execve。

所以 PIE 和 Full RELRO 在这题里都很尴尬：它们保护的是程序里的地址和 GOT，但 shellcode 根本不碰这些。

思考 06｜既然程序是 PIE、Full RELRO，为什么不用 system@plt？

三个原因：

  1. PIE 让程序基址随机，system@plt 的运行时地址 = 基址 + 固定偏移。我们不知道基址，写死会跳错。
  2. 就算拿到基址，还需要参数：一个 /bin/sh 字符串，外加一个能把地址放进 RDI 的 gadget。程序里不一定有现成的。
  3. Full RELRO 让 GOT 只读，GOT 劫持也走不通。

而 shellcode 完全绕开这些：它不调用程序里的任何函数，只依赖内核的 syscall。这也是 ret2shellcode 在“有 RWX 页”时最省事的原因。

如果这题没有 mmap，PIE + NX + Full RELRO 的组合就会逼你走 ret2libc：先泄漏一个 libc 地址，再算 system 和 /bin/sh，最后 ROP。那是下一阶段的内容。

思考 07｜shellcode 里为什么一个 0x00 都没有？明明这题用的是 read，二进制安全。

因为 shellcraft 默认生成的是 null-free shellcode，这是一个历史习惯，也是一个好习惯。

早期的栈溢出大量使用 strcpy、gets、scanf("%s") 这类字符串函数，它们遇到 \x00 就停下。如果 shellcode 里出现空字节，写进去的代码会被截断，执行到一半就崩。

所以 shellcraft 会用各种技巧避开空字节，比如这里的异或：

如果直接 push 0x006873，机器码里就会带 0x00。先压一个“异或过的值”，再在栈上异或回来，就能既得到 "sh"，又不让空字节出现在代码里。

这题的 read 是二进制安全的，空字节其实也能写进去。但用默认的 null-free shellcode 不会有任何坏处，换个入口也照样能用。

思考 08｜shellcode 最后是 syscall，没有 ret，执行完怎么“回来”？

不需要回来。

execve("/bin/sh", ...) 成功时，内核会用 /bin/sh 替换掉当前进程的整个映像。也就是说，syscall 之后，执行的已经不是原来那个程序了，栈、代码段、返回地址全被换掉。

对原来的程序来说，这个 syscall 永远不会返回。所以 shellcode 不需要 ret，也不需要保存/恢复任何寄存器。

如果 execve 失败（比如 /bin/sh 不存在），syscall 会返回一个负的错误码，然后 CPU 继续往下执行——但这时候后面是 mmap 页里的 0，马上就会崩。所以 shellcode 的正确性依赖于 execve 成功。

如果你想写一段“执行完还能回来”的 shellcode，那就得自己加 exit 或者 ret，并且保证栈没被破坏。这题不需要。

为什么不能一口气发完

先明确一件事：read(0, buf, 0x100) 的 0x100 是最多读多少，不是“必须读满 0x100”。

在 socket 上，read 的行为是：

  • 只要内核缓冲区里有数据，就返回已经读到的字节数；
  • 不会等到凑满 0x100 才返回。

现在假设你把 shellcode 和 payload 一口气发过去：

TCP 是字节流，没有“消息边界”。这两段数据很可能被合并成一个包，或者至少同时躺在内核缓冲区里。

这时程序执行到第一次 read，它会把能读到的都读走，最多 0x100 字节。shellcode 只有 48 字节，payload 是 64 字节，加起来 112 字节，小于 0x100——于是第一次 read 会把 shellcode 和 payload 全部吞进 buf。

然后程序打印 Anything else?，执行第二次 read。但数据已经被第一次读光了，第二次 read 只能干等。

结果就是：程序卡住，exp 超时。

正确的时序

第一次 read 返回之后，程序才会打印 Anything else?。所以这句话本身就是一个天然的同步点：

时间线：

recvuntil(b'Anything else?\n') 能返回，说明：

  1. 第一次 read 已经返回了；
  2. 程序已经走到第二次 read 前面。

这时候再发 payload，就不会被第一次 read 吃掉。

第一个 recvuntil 其实不是严格必须的——数据先到 socket 缓冲区，read 照样能读到。但加上它有两个好处：确认程序已经启动、把提示从缓冲区里清掉，后面的收发对照起来更干净。

思考 09｜两次 send 之间不加 recvuntil，一定会失败吗？

不一定“每次”都失败，但不可靠，而且失败时的现象很迷惑。

关键在 TCP 的字节流特性：两次 send 的数据可能被合并、可能分开发送、也可能在接收端被一次 read 全部取走。第一次 read 的上限是 0x100，而 shellcode + payload 只有 112 字节，完全在它的胃口之内。

  • 如果两次数据被操作系统分成了两个包，并且程序在第二个包到达之前已经执行完第一次 read，那可能侥幸成功；
  • 如果两个包几乎同时到达，第一次 read 就会把 payload 的开头一起读走，第二次 read 等不到数据，exp 卡死。

所以正确的写法不是“赌它成功”，而是用程序自己的输出做同步。puts("Anything else?") 是第一次 read 之后才执行的，它就是最可靠的屏障。

这也是 pwn 里一个通用的习惯：能 recvuntil 就 recvuntil，不要靠 sleep 赌时序。

知识点补充

1. ret2shellcode 和前面几种技术的关系

技术 前提 代码从哪来 这题为什么不用
ret2text 程序里有现成后门 程序自带 没有后门
ret2shellcode 有可写可执行内存 我们输入的机器码 这题就是
ret2plt 程序导入过目标函数，地址固定 程序 + libc PIE 开了，PLT 地址不固定
ret2libc / ROP 能泄漏 libc，或有足够 gadget 程序 + libc 不需要，shellcode 更直接

这几项不是互相替代的关系，而是看程序给了什么条件：

  • 有后门 → ret2text；
  • 有 RWX 页 → ret2shellcode；
  • 有固定 PLT → ret2plt；
  • 什么都没有但有泄漏 → ret2libc / ROP。

这题的条件太舒服了：程序亲手 mmap 了一块 RWX，还把地址写死在代码里，几乎是白给。

2. mmap 参数速查

prot 的位：

值 含义
1 PROT_READ 可读
2 PROT_WRITE 可写
4 PROT_EXEC 可执行
7 RWX，三个都有

flags 常见位：

值 含义
0x02 MAP_PRIVATE 私有映射
0x10 MAP_FIXED 强制使用给定地址
0x20 MAP_ANONYMOUS 匿名映射
0x22 MAP_PRIVATE + MAP_ANONYMOUS，这题的组合

mmap 失败时返回 MAP_FAILED，也就是 (void *)-1，不是 NULL。这题的程序没有检查返回值；如果映射失败，buf = -1，第一次 read 会失败，后面就全错了。实际运行时它是成功的。

3. 为什么 PIE 管不到 0x233000

PIE 的随机化对象是 ELF 映像的加载基址，包括代码段、数据段、GOT 这些。

0x233000 是程序自己调用 mmap 请求的一块匿名内存，和 ELF 映像没有关系。它不在 PIE 的随机化范围里。

不过这里还有一个细节：mmap 的第一个参数在没有 MAP_FIXED 时只是建议地址。内核会先尝试在这个地址附近分配；如果这块区域空闲，就照办；如果不空闲，就换个地方。这题能稳定拿到 0x233000，是因为它页对齐、地址低、区域空闲，并且高于 mmap_min_addr。详细的分析见上面思考 02。

所以这题才能把 0x233000 写死。换成别的程序、别的环境，最好先在 gdb 里确认一下。

5. 为什么 NX 拦不住 PROT_EXEC

NX（No eXecute）在 x86-64 上对应页表里的 XD 位。它控制的是每一页能不能被取指执行。

  • 栈、堆默认映射成 rw-，没有 x，所以 NX 能拦住“把 shellcode 放栈上执行”；
  • mmap 的 prot = 7 显式带了 PROT_EXEC，内核就把这一页映射成 rwx，XD 位是清掉的。

所以 NX 不是“禁止一切非代码段执行”，而是“默认不给执行权限”。只要程序自己申请了可执行内存，NX 就管不着。

这也是为什么看 checksec 不能只看结论，还要看程序怎么管理内存。看到 mmap、mprotect，就要多留个心眼。

6. shellcode 的大小和长度限制

shellcraft.sh() 在 amd64 上生成的 shellcode 大约是 48 字节（不同 pwntools 版本可能略有差异）。这题的第一次 read 上限是 0x100 = 256 字节，绰绰有余。

如果 shellcode 超过 0x100，read 只会读前 256 字节，后面的代码不会写进去，执行到一半就会崩。遇到这种情况，常见做法是：

  • 换更短的 shellcode；
  • 分成多次 read 写入；
  • 找一个更大的缓冲区。

7. 如果 mmap 的权限不是 7

prot 权限 结果
7 rwx 可以直接执行 shellcode
5 r-x 可执行但不可写，read 写不进去
3 rw- 可写但不可执行，NX 生效，shellcode 跑不起来
1 r-- 只读，什么都干不了

如果是 rw-，就得走 ROP：泄漏 libc、找 gadget、构造链。这也是为什么这题的条件算“白给”。

8. 如果输入函数换成 gets / strcpy

这题两次都是 read，二进制安全，\x00 和 \n 都能原样写进去。

如果换成 gets 或 strcpy：

  • \x00 会被当成字符串结束，shellcode 和 payload 都可能被截断；
  • \n 在 gets 里会结束输入。

这时候就必须用 null-free 的 shellcode（shellcraft 默认就是），并且 payload 里不能出现 \n。这也是 CTF 里经常要检查 payload 字节的原因。

9. 如果这题没有 mmap

那 0x233000 就不存在，只能回到 ROP：

  • 有现成后门 → ret2text；
  • 有固定 PLT → ret2plt；
  • 都没有 → 泄漏 libc → ret2libc。

或者，如果栈可执行（NX 关闭），可以直接把 shellcode 放栈上，返回地址指向栈。但那需要知道栈地址，通常要靠泄漏。

所以这题的 mmap 是出题人给的“捷径”，不是常规情况。现实中遇到 mmap(PROT_EXEC) 要格外警惕，这基本等于把代码执行的大门打开了。

几个容易踩的坑

# 坑 现象 正确做法
1 偏移写成 0x28 + 8 返回地址少覆盖 8 字节，ret 跳到 0x4141... 0x30 + 8 = 0x38，别漏掉 buf 指针
2 两次 send 之间没有 recvuntil 第一次 read 把 payload 一起吃掉，第二次 read 卡死 用 Anything else? 做同步
3 把 shellcode 和 payload 拼在一起发 同上，exp 超时 分两次发，中间等提示
4 忘了 context(arch='amd64') 生成了 32 位 shellcode，执行时非法指令 在 shellcraft.sh() 之前设置 arch 和 os
5 在 PIE 下还去 IDA 抄程序地址 运行时地址对不上，跳到错误位置 这题只需要 0x233000，不需要程序内地址
6 用 p32 打包 0x233000 地址被截断，ret 跳到错误位置 64 位一律 p64
7 没验证 mmap 地址 本地/远程环境不同，0x233000 可能不是映射起点 gdb vmmap 确认，或看 [rbp-8]
8 shellcode 超过 0x100 只写进去前 256 字节，执行到一半崩 len(shellcode) 检查，必要时分段写
9 远程忘了 TLS 连接重置或收不到提示 平台要求时加 ssl=True, sni=HOST
10 只看 checksec 就下结论 以为 NX + PIE 只能 ROP，错过 RWX 页 一定看 main 里有没有 mmap / mprotect

还有一个更细的坑：理论上第一次 read 也可能只读到一部分 shellcode（TCP 不保证一次 send 对应一次 read），剩下部分会被第二次 read 当成 payload 读走。一次 48 字节的小包在正常网络里几乎总是一起到，但如果远程偶发失败，先排查同步，再怀疑拆包。

小结

这题看起来保护很吓人，实际上程序自己把路铺好了。把整道题拆开，其实就四件事：

  1. checksec 只是默认保护，不是程序运行时的全部。 程序自己 mmap 了一块 rwx 页，NX 就管不到它；这块页也不在 PIE 的随机化范围里。
  2. ret2shellcode 需要三个条件：一块可执行内存、能把它写进去、能跳过去。这题三个条件全满足。
  3. 偏移要按编译器的实际布局算：v4 后面还有 buf 指针，所以是 0x30 + 8，不是 0x28 + 8。
  4. 两次输入之间要同步：TCP 是字节流，read 不会等凑满 0x100；不 recvuntil 就可能让第一次 read 把 payload 吃掉。

如果只记一句话：看到 mmap 的 prot 是 7，先别管 NX，先想想能不能塞 shellcode。

最后留三个问题，你可以自己想一想：

  1. 如果 mmap 的 prot 改成 3（可读写但不可执行），这题还能怎么打？需要先泄漏什么？
  2. 如果第一次 read 只允许读 8 字节，而你的 shellcode 有 48 字节，你会怎么把完整的 shellcode 送进去？
  3. 如果这是 32 位程序，shellcode 和 exp 会怎么变？还需要 mmap 吗？

下一步可以试试：没有 mmap 的 ret2libc、开了 PIE 但能泄漏地址的 ret2plt，或者把 shellcode 换成 shellcraft.cat('/flag')，看看能不能少一步交互。
