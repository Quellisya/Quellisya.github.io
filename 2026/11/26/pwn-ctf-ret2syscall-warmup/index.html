一分钟速览

  • 难度：入门偏进阶（比 ret2shellcode 难一档：没有现成 gadget，要自己造链，还要自己做栈迁移）
  • 考点：ret2syscall、32 位系统调用约定、int 0x80、用 read / write 的返回值控制 eax、栈迁移、add esp gadget、ORW、pwntools
  • 保护：No RELRO、No Canary、NX enabled、No PIE（0x8048000）、statically linked、stripped
  • 漏洞：addr[32]，却 read(0, addr, 0x34)；溢出 0x14 字节 = 4 字节返回地址 + 0x10 字节栈上数据
  • 关键地址：START=0x080480d8、SYS_READ=0x0804811d、SYS_WRITE=0x08048135、SYSCALL=0x08048122、ADD_ESP=0x080481b8、SYS_EXIT=0x0804814d、BUF=0x08049000
  • 核心思路：没有 pop eax → 先 read(0, BUF, 11)，让 eax = 11 → 跳到 0x8048122（跳过 mov eax,3）→ int 0x80 → execve("/bin/sh", NULL, NULL)
  • 核心难点：一次只能写 0x34 字节；ret 回 start，每轮 sub esp,0x10 把栈往下挪一格，链必须倒着写
  • 结果：拿到 shell，cat /flag 得到 CTF2{3a316961-2799-40b2-9070-2202546dd89e}
  • 思考题：文中有 14 道，答案默认折叠，建议先自己想一遍

阅读说明

  • 前置知识：栈溢出、返回地址、32 位 cdecl 栈传参、ROP 的基本概念（做过 ret2text / ret2plt 更好）。系统调用不熟也没关系，正文会从头讲。
  • 工具：file、checksec、IDA、ROPgadget、gdb + pwndbg、pwntools
  • 环境：Linux（Kali / Ubuntu）。文中的靶场地址是当时的临时环境，现在多半已经失效，请换成自己的靶场或本地环境
  • 本文所有操作仅用于授权靶场和本地环境，请勿对未授权的目标做任何测试

做题路线

file / checksec → IDA 看 start → 认出 read / write / exit 三个 wrapper → 找溢出 → 发现没有 pop eax → 用 read 返回值控 eax → 想清楚怎么把长链塞进 0x34 → 回 start 做栈迁移 → 找 add esp gadget → 拼链 → 倒序发送 → shell 或 ORW

先把程序看明白

这道题和前面几道不太一样。前面是“程序里有个后门”或者“程序里导入了 system”，这题是程序里什么库都没有，只剩系统调用。

看到这张表，第一反应通常是：NX 开着、没有 PIE，那就找 gadget 打 ROP。方向没错，但这题会给你两个意外：

  1. 程序小得离谱，ROPgadget 几乎找不到东西，连一个 pop eax; ret 都没有；
  2. 一次只能写 0x34 字节，一条正常的 ROP 链根本塞不下。

先把程序摊开看。

整个 .text 只有两百多字节

用 objdump 反汇编，代码从 0x80480d8 到 0x80481bb，一共也就两百多字节：

看完这段，有两个细节非常刺眼：

  • 所有的“函数”最后都落到 int $0x80（0x8048116、0x804812e、0x8048146、0x8048157 这几处）。这说明它们不是 libc 函数，而是手工写出来的系统调用包装器。
  • 整个程序没有一处调用外部库。statically linked 在这里的真实含义是：它自己就是全部，没有 glibc。

这就决定了这题的打法：没有 system、没有 execve@plt，唯一能用的“出口”就是 int 0x80。

思考 01｜file 说是 statically linked，为什么还说“没有 libc”？静态链接不是应该把 libc 打进去吗？

通常的“静态链接程序”确实会把 glibc 一起链进来，那种二进制动辄几百 KB 到几 MB，system、execve、成千上万个 gadget 都在。

但这题不一样：它只有两百多字节的 .text、6 个函数，而且每个函数都是三五行汇编加一句 int 0x80。这不是“链了 glibc 的静态程序”，而是手写汇编、自己实现 _start、直接向内核发系统调用的极小二进制。

file 说 statically linked，只是因为它没有 .interp、不依赖动态加载器；它并没有说“带了 libc”。这两件事经常被混为一谈，看到几 KB 的“静态”程序时尤其要留个心眼。

IDA 里看 start

用 IDA 打开，函数列表里只有 6 个：

四个调用，对应四件事：

  1. sub_804810D(0xA)：alarm(10)。给整个程序上了一个 10 秒的闹钟；
  2. sub_8048135(1, "Welcome to 0CTF 2016!\n", 0x16)：往标准输出写一句欢迎语；

注意一个很关键的细节：这些函数的参数是从栈上取的（[esp+4]、[esp+8]、[esp+0xc]），因为它们遵守 32 位 cdecl 调用约定；但它们内部又把参数搬进 ebx、ecx、edx，因为系统调用要求用寄存器传参。

所以它们同时体现了两套约定：

  • 从外面看：普通函数，参数在栈上；
  • 从里面看：系统调用，参数在寄存器里。

这个“双面人”特性，正是我们能拿 ROP 调它们的根本原因——ROP 天然就是在栈上摆参数。

有漏洞的 sub_804815A

图 7：addr[32] 却读了 0x34 字节

对应汇编：

一条一条看：

  1. sub esp,0x30：给本次调用分配 0x30 字节栈空间；
  2. lea eax,[esp+0x10]：缓冲区 addr 从 esp+0x10 开始；
  3. read(0, addr, 0x34)：从标准输入读 0x34 = 52 字节；
  4. write(1, "Good Luck!\n", 0xb)：读完之后打印一句，这是个天然的同步点；
  5. 七个 mov $0xdeadbeaf：把 eax、ecx、edx、ebx、esi、edi、ebp 全写成 0xdeadbeaf；
  6. add esp,0x30; ret：恢复栈并返回。

漏洞在第 3 步：addr 只有 0x20 = 32 字节，却读了 0x34 = 52 字节。从 addr 起点到返回地址正好是 0x20，所以溢出量是：

也就是 4 字节返回地址 + 返回地址上方 16 字节。

第 5 步的“寄存器清零”不是随手写的，它是故意恶心人的：读完之后，read 的返回值（读了多少字节）本来好好躺在 eax 里，结果被 0xdeadbeaf 一把盖掉。后面我们会看到，这个细节直接决定了利用思路。

思考 02｜IDA 把 sub_804815A 反编译成 return 0xDEADBEAFDEADBEAFLL，这个返回值是真的吗？

不是。汇编里根本没有“返回一个 64 位数”这回事，它是把 eax、ecx、edx、ebx、esi、edi、ebp 七个寄存器逐个赋成 0xdeadbeaf，然后 add esp,0x30; ret。

IDA 看到 eax 和 edx 被赋值，就顺手把它猜成“返回一个 64 位数”（高 32 位 edx，低 32 位 eax），于是写出了 0xDEADBEAFDEADBEAFLL。这只是反编译器的猜测，不是程序的真实语义。

反编译结果要对照汇编看，尤其是这种手写汇编的题。IDA 的 C 代码是“方便你读”，不是“标准答案”。

系统调用：用户态和内核之间的那道门

在继续之前，得先把系统调用讲清楚，不然后面 eax = 11 这种事会很突兀。

一句话：用户态不能直接干活

你的程序运行在用户态，不能直接读文件、开进程、退出，这些都得请求内核。请求的方式就是“系统调用”（system call）。

在 x86 上，进入内核有两道常见的门：

  • 32 位：int 0x80（软中断）
  • 64 位：syscall（专门的快速系统调用指令）

CPU 执行到这条指令，就从用户态切到内核态；内核根据寄存器里的系统调用号决定要干什么，干完再把结果写回寄存器，切回用户态。

32 位和 64 位的传参约定

这是这题最核心的前置知识，直接列成表：

项目 32 位 i386 64 位 x86_64
进门指令 int 0x80 syscall
系统调用号 eax rax
第 1 个参数 ebx rdi
第 2 个参数 ecx rsi
第 3 个参数 edx rdx
第 4 个参数 esi r10
第 5 个参数 edi r8
第 6 个参数 ebp r9
返回值 eax rax

两个容易记混的点：

  • 64 位的第 4 个参数是 r10，不是 rcx。因为 syscall 指令本身会把返回地址放进 rcx、把标志位放进 r11，所以 rcx 被占用了，只能用 r10 顶替。
  • 返回值也在 eax / rax 里，如果是负数，通常表示 -errno。这一点后面会变成我们的“武器”。

普通函数调用 vs 系统调用

这是很多人第一次接触系统调用时最容易绕晕的地方：

普通函数调用（cdecl） 系统调用
谁规定的 编译器 / ABI 内核 / CPU 指令
参数放哪 栈上 寄存器
返回地址 call 压栈 不进用户栈，syscall 自己处理
返回值 eax eax / rax

所以，“32 位传参走栈”这句话只说对了一半：普通函数走栈，系统调用走寄存器。

这题里的 sub_804811D 恰好站在两者的交界处：它作为普通函数被 call，参数从栈上拿；但它内部又把参数放进寄存器，再 int 0x80。理解了这个“翻译层”，后面的 ROP 块就很好懂了。

常见系统调用号

功能 i386 号 x86_64 号
exit 1 60
read 3 0
write 4 1
open 5 2
close 6 3
execve 11 59
alarm 27 37

这题会用到编号 3 的 read、编号 4 的 write、编号 5 的 open、编号 11 的 execve、编号 1 的 exit、编号 27 的 alarm。

思考 03｜为什么系统调用不像普通函数那样用栈传参，非要占用一堆寄存器？

几个原因叠在一起：

  1. 内核不信任用户栈。系统调用要切到内核栈执行，参数如果还留在用户栈上，内核就得回头去读用户内存，既慢又容易出 TOCTOU 之类的问题。
  2. 寄存器的约定是 CPU 指令的一部分。int 0x80 / syscall 一执行，CPU 已经切到内核，内核最自然的取参数位置就是寄存器。
  3. 快。寄存器访问比内存快，系统调用又非常频繁，能省一点是一点。64 位的 syscall 比 32 位的 int 0x80 还快，就是因为少了中断门那一套开销。

代价是参数数量受限（寄存器就那么几个），而且第 4 个参数在 64 位下还得避开被 syscall 占用的 rcx。

ret2syscall 到底在做什么

现在可以正面回答标题里的词了。

ret2syscall（有些资料写作 ret2systemcall，本文两种叫法都指同一件事）指的是：用 ROP 把寄存器摆成系统调用需要的样子，然后跳到一条 int 0x80 / syscall 指令上。

它和 ret2libc 的区别是“调谁”：

  • ret2libc：跳到 libc 里的 system / execve 函数；
  • ret2syscall：不经过任何库，直接让内核干活。

思考 04｜为什么这题不能像平时那样，找 pop eax; ret 之类的 gadget 拼一条标准链？

两个原因叠加：

  1. 程序太小。整个 .text 只有两百多字节、6 个函数，ROPgadget 扫出来的有用 gadget 极少，pop eax; ret 这样的序列压根不存在。
  2. 它是手写汇编，不是编译器生成的代码。编译器生成的代码里，函数序言/尾声会顺带产生大量 pop、leave 之类的字节序列；手写汇编没有这些“副产品”。

所以标准模板在这里失效。能用的只有程序自带的几个东西：

  • 三个 wrapper 里的 mov eax, 3/4；
  • 半截函数 0x8048122（只搬参数、不动 eax）；
  • 0x80481b8 的 add esp,0x30; ret；
  • 以及系统调用自己会把返回值写进 eax 这件事。

最后一条，就是破局的关键。

没有 pop eax，那就借 read 的返回值

先把结论摆出来：

系统调用的返回值会写进 eax。read 返回读了多少字节，write 返回写了多少字节。既然没有 pop eax，那就让 read 帮我们把 eax 写成想要的值。

我们想要 eax = 11，也就是 execve 的调用号。那就先调一次 read(0, BUF, 11)：读 11 个字节，read 返回 11，eax 自然就是 11。

然后，关键在于往哪儿跳。read 的 wrapper 入口是 0x804811d，它第一句是 mov eax, 3。如果直接跳回 0x804811d，eax 会被改成 3，前功尽弃。

但函数中间还有一条指令：

从 0x8048122 进去，就跳过了 mov eax, 3，只做“搬参数 + int 0x80”这两件事。eax 保持原样，也就是 read 刚留下的 11。

思考 05｜为什么跳到 0x8048122，而不是回到 0x804811d？

因为 0x804811d 的第一条指令是 mov eax, 3，会把我们辛苦攒出来的 eax = 11 改成 3，int 0x80 就变成又读一次，而不是 execve。

0x8048122 是函数中间的一条指令，从它开始执行，刚好跳过 mov eax, 3，只保留“把参数搬进 ebx/ecx/edx 然后 int 0x80”这部分。这种“从一个函数中间切进去”的用法在 pwn 里很常见，叫 mid-function gadget（半截函数 gadget）。

判断能不能这么切，看两点：切进去之后的指令序列是不是你想要的；以及切进去之前有没有需要保留的寄存器被改掉。这里是后者：eax 必须保住。

思考 06｜vuln 里那次 read 也返回了字节数，为什么不能直接用它的返回值？

因为 sub_804815A 在 ret 之前，把 eax、ecx、edx、ebx、esi、edi、ebp 全部写成了 0xdeadbeaf。

也就是说，read 的返回值确实产生过，但在我们拿到控制权之前就被销毁了。出题人这一段不是多余的，它专门堵死“直接用第一次 read 返回值”这条捷径。

所以只能在 ROP 链内部再调一次 read：这一次的返回值发生在链执行过程中，不会再被 0xdeadbeaf 覆盖，可以一直保留到下一个 gadget。

一次只能写 0x34：回到 start，把栈一格格挪下去

思路有了，但马上撞上第二个问题：链塞不下。

execve 版需要 read 和 SYSCALL 两段：read 那一块按后面的块结构是 0x38 字节，SYSCALL 作为链尾没有填充，只占 0x14 字节，加起来 0x4C 字节。而 vuln 一次只读 0x34 字节，其中 0x20 还是缓冲区，真正能用来放链的只有 0x14。

直觉是：ret 回 read 再读一次不就行了？

不行。看一眼 vuln 的结尾：

add esp,0x30 会把栈抬回调用前的位置。如果你 ret 回 read，下一次 read 的缓冲区还在同一个地方，会把你上一轮刚写的数据覆盖掉，什么也攒不下来。

正确的做法是：ret 回程序入口 start（0x80480d8）。

start 一进来就是：

它先把栈往下压 0x10。于是下一轮的整个 start 帧、vuln 帧、read 缓冲区，都比上一轮低 0x10。上一轮写在返回地址上方的 16 字节，正好留在新帧的上方，不会被覆盖。

这就是“每轮只保留 0x10 字节”的栈迁移。

链为什么要倒着写

栈是往低地址长的：最后写的那一轮，地址最低；而 ret 从最低的链头开始执行。

所以：

  • 第一次 send 写的是链尾（高地址）；
  • 最后一次 send 写的是链头（低地址）。

exp 里的 reversed(range(...)) 就是在做这件事：从链尾往链头写。

思考 07｜为什么一定要 ret 回 start，而不是 ret 回 vuln 自己，再读一次？

因为 vuln 结尾有 add esp,0x30。

ret 回 vuln 时，vuln 会重新执行 sub esp,0x30，缓冲区又回到和上一轮完全相同的位置。下一次 read 会把你上一轮写的东西原地覆盖，链永远长不大。

start 不一样：它一进来就 sub esp,0x10，带着整个调用链往下挪 0x10。这样每一轮的缓冲区都错开 0x10，上一轮的 16 字节才能被保留在“新帧的上方”。

所以这不是“回哪里都行”，而是只有带 sub esp 的入口才能做这种逐格迁移。

思考 08｜为什么链要倒着写？正着把第一块先发过去不行吗？

不行，因为执行顺序和写入顺序是相反的。

栈往低地址长，每轮写入的位置比上一轮低 0x10。而 ret 是从最低地址那条返回地址开始执行的。也就是说，最后写的那一轮，才是最先执行的那一轮。

所以：

  • 想最先执行的块 → 最后发；
  • 想最后执行的块 → 最先发。

reversed(range(4, len(exploit), 0x10)) 就是把 exploit 从尾巴往前切片，先发尾块，最后发头块。

思考 09｜add esp,0x30 里的 0x30 是随便选的吗？换成 add esp,0x20 行不行？

为什么块 1 的下一跳是 SYS_EXIT？因为正常情况下 execve 会把整个进程替换掉，int 0x80 不会返回；但如果 execve 失败（比如路径不对），链会继续往下走，跳到 SYS_EXIT 干净地退出，而不是掉进一堆填充字节里崩掉。

read 读进来的 11 字节是 "/bin/sh\x00AAA"：

  • 前 8 字节 "/bin/sh\0" 是路径；
  • 后 3 字节 "AAA" 只是凑数，让 read 的返回值正好是 11。

execve 的第二个参数 argv 传 NULL 在 Linux 上是可以的，内核会把它当成空参数数组；第三个参数 envp 也传 NULL。

思考 10｜为什么 read 一定要读 11 个字节？读 8 个不行吗？

因为这条链把“read 的返回值”直接当成“下一个系统调用的编号”。

  • 读 11 个字节 → eax = 11 → execve；
  • 读 8 个字节 → eax = 8 → i386 的 8 号系统调用是 creat，链子就去做别的事了，拿不到 shell。

这不是巧合，是设计：read 的长度参数，就是下一个系统调用的编号。想让 eax 等于几，就让它读几个字节（前提是输入确实有那么多字节）。

同理，ORW 版本里 write(1, BUF, 5) 返回 5，正好把 eax 变成 open 的编号 5。这是在纯 syscall 题里非常常见的手法：用上一个系统调用的返回值，喂给下一个系统调用当编号。

思考 11｜如果 read 没有读满 11 字节（比如只到了 5 字节），会发生什么？

eax 就会等于实际读到的字节数，而不是 11。

假设只到了 5 字节：eax = 5，接下来 SYSCALL 会执行 open(BUF, 0, 0) 而不是 execve。BUF 里是半截 "/bin/"，open 失败返回负数，然后 test eax,eax; js 跳到 SYS_EXIT，程序直接退出，你只看到连接断开。

所以这条链对 read 的返回值极其敏感。发送 "/bin/sh\0AAA" 的 11 字节很小，正常情况下一次就到；如果偶发失败，先检查同步和网络，别急着改链。

思考 12｜为什么每一轮都要 recvuntil，不能把 5 轮数据一次性 send 完？

乍一看可以：每次 read 上限是 0x34，我每轮也正好发 0x34，流水线发过去，第一次 read 吃 52 字节，第二次吃 52 字节，似乎没毛病。

问题在于：read 不保证一次读满。TCP 是字节流，read 只要缓冲区里有数据就会返回，可能只返回 40 字节，剩下的 12 字节被下一轮 read 吃掉。一旦读到的字节数不是 52，每一轮的栈写入位置就整体错位，链直接崩。

用程序自己的 Welcome 输出做同步，能保证“上一轮 read 已经结束、当前轮 read 即将开始”。这是 pwn 里的通用习惯：能用 recvuntil 就别用 sleep 赌时序。

思考 13｜为什么最后要补 B 到 0x34？少发几个字节不行吗？

补满是为了让每轮 read 消耗固定 52 字节，保证栈写入位置严格按 0x10 下移。

如果你少发几个字节，read 就会少读几个，下一轮的缓冲区位置虽然还是由 sub esp,0x10 决定，但上一轮只写了一部分的 16 字节区域会留下旧数据，链里就会出现空洞或错位。

补出来的 B 都在链的有效范围之外，链在执行到它们之前就已经 execve 成功或 exit 了，所以它们不会被当成代码。

ORW 版：不 execve，也能读 flag

execve 版已经能拿 shell 了。但如果程序被 seccomp 禁掉了 execve，或者你想练“把多个系统调用串起来”，就得走 ORW：open → read → write，自己把文件内容读出来。

这题的 ORW 版和 execve 版是同一套骨架，只是链更长，正好用来说明“用返回值串系统调用”的威力。

每一步的 eax 是怎么走的

块 调用 返回值 / 结果
0 read(0, BUF, 6) 读入 "/flag\0"；eax = 6，但下一块会重设 eax
1 write(1, BUF, 5) 打印 "/flag"；eax = 5 → 正好是 open 的号
2 SYSCALL(BUF, 0, 0) open(BUF, O_RDONLY, 0)；返回 fd = 3
3 read(3, BUF, 0x100) 把 flag 读进 BUF；eax = 实际长度
4 write(1, BUF, 0x100) 打印 flag（后面跟一串 \0）

几个设计点：

块 1 为什么用 write(1, BUF, 5)，而不是 write(1, BUF, 6)？
因为第三个参数在这里“一箭双雕”：它既是写出的字节数（5，正好是 "/flag"），又是 write 的返回值，进而成为下一个系统调用的编号。SYS_OPEN = 5 这个常量就是拿来当长度用的。如果写成 6，eax 就变成 6，下一个系统调用就变成 close 去了。

块 2 为什么用裸的 SYSCALL 而不是 SYS_* wrapper？
因为 open 的调用号 5 已经在 eax 里了，任何 mov eax, 3/4 的 wrapper 都会把它改掉。0x8048122 只搬参数、不碰 eax，正好。

块 3 为什么从 fd = 3 读？
open 返回的 fd 没有地方存（没有 mov ebx, eax 之类的 gadget），但 Linux 分配 fd 是“当前最小的可用值”。进程启动时 0/1/2 已经被占用，程序也没开别的文件，所以第一个 open 稳定返回 3。这是环境特性，不是语言保证。

最后一块为什么写 0x100 字节，而不是 flag 的实际长度？
因为 read(3, ...) 的返回值在 eax 里，要把它当 write 的长度，需要 mov edx, eax 之类的 gadget，这题没有。所以只能写一个足够大的固定长度，多打印的 \0 无害。

思考 14｜open 返回的 fd 为什么可以直接写死成 3？如果环境变了还成立吗？

成立的前提是：进程启动时 0/1/2 已经分别对应标准输入、标准输出、标准错误，而且程序在这之前没有打开过别的文件。Linux 的 open 返回“当前最小的可用 fd”，所以第一个 open 就是 3。

在远程环境里，0/1/2 通常都被服务框架 dup 成同一个 socket，fd 3 空着，所以能稳定拿到 3。

但这个假设不牢靠：如果程序之前 open 过日志、加载过配置，或者服务端用了额外的 fd，返回值就不是 3 了。稳妥的做法是用 openat、先 close(0) 腾出 fd，或者干脆泄漏 open 的返回值——只是这题没有那样的 gadget，所以只能依赖环境固定。

CTF 里“环境固定”是可以接受的近似；真实漏洞利用里，这种写死要格外小心。

知识点补充

1. 为什么这题不能用 ret2libc

技术 前提 这题为什么不行
ret2text 程序里有后门 没有后门
ret2shellcode 栈或 RWX 页可执行 NX 开着，栈不可执行
ret2plt 程序导入过目标函数 没有动态链接，没有 PLT
ret2libc 有 libc，能泄漏地址 根本没有 libc
ret2syscall 有 int 0x80 / syscall 就是这题

file 说 statically linked，但前面已经解释过：它没有链 glibc，是纯手写汇编。所以 system、execve 这些符号都不存在，唯一的路就是自己摆寄存器、自己 int 0x80。

2. 用返回值控制寄存器：一个通用套路

系统调用 返回值 可以拿来当什么
read 读到的字节数 任意系统调用号（读到几就是几）
write 写出的字节数 任意系统调用号
open 文件描述符 后续 read / write 的第一个参数
brk / mmap 地址 后续读写的目标

这题用了前两条：

  • read(11) → eax = 11 → execve；
  • write(5) → eax = 5 → open。

在纯 syscall 题里，看到“没有 pop eax”别慌，先找找有没有 read / write：它们天然会往 eax 里写一个可控的数。

3. 栈迁移的两种思路

方式 代表指令 特点
少量多次 ret 回带 sub esp,0x10 的入口 每轮挪一小格，适合一次写不完的题
一次性大迁移 leave; ret、pop rsp、xchg esp, eax 直接把 esp 指到一块可控内存

这题是前者：没有能一次搬走栈的 gadget，只能靠 start 的 sub esp,0x10 一格格挪。后者在有大块可控内存（比如堆、.bss）时更常见。

4. alarm(10) 的两个影响

start 每轮都会执行 alarm(10)：

  1. 每轮重设 10 秒。如果某一轮交互太慢（比如在 gdb 里单步），进程会被 SIGALRM 杀掉。
  2. 闹钟会跨 execve 保留。拿到 shell 之后，原来那个 10 秒的定时器还在，所以别磨蹭，尽快 cat /flag。这也是为什么很多 pwn 题拿到 shell 后要马上读 flag，而不是先 ls 半天。

（在 Linux 上，alarm() 设置的定时器确实会跨 execve 保留；如果换系统或换实现，行为可能不同。）

5. 如果 NX 关了会怎样

如果这题 NX 关闭，栈可执行，那根本不用这么麻烦：直接把 shellcode 放 addr，覆盖返回地址为栈地址就行——就是上一题 ret2shellcode 的套路。

但 NX 开着，栈上的字节只能读不能执行，所以只能走 ROP / syscall。这也是为什么这题要绕这么大一圈。

11 拿 shell send("/bin/sh\0AAA") cat /flag
12 ORW 变体 read → write → open → read → write 不依赖 execve 也能读 flag

小结

这题看起来只是一道“ret2syscall 入门”，实际上把三个很通用的技巧串在了一起。拆开来看，就四件事：

  1. 没有 pop eax 时，系统调用的返回值就是最好的 set register。 read 读几个字节，eax 就是几；write 写几个字节，eax 就是几。纯 syscall 题里，这是最常用的“造数”手段。
  2. wrapper 是双面人：外面 cdecl，里面 syscall ABI。 它从栈上取参数，再把参数搬进寄存器。正因为如此，我们才能用 ROP 在栈上摆好参数去调它。
  3. 栈迁移不是玄学。 start 的 sub esp,0x10 就是那个“往下挪一格”的工具；链要从尾往头写，因为最后写的那一轮地址最低、最先执行。
  4. ADD_ESP 是 cdecl 参数和 ROP 链之间的桥。 没有它，read 的参数会被下一个 gadget 当成自己的参数，链立刻崩。

如果只记一句话：没有 pop 就去找 mov 或者返回值；一次写不下就回入口，把栈一格格挪。

最后留三个问题，你可以自己想一想：

  1. 如果出题人把 sub_804815A 结尾的 add esp,0x30 去掉，栈迁移会变简单还是变难？还能怎么攒链？
  2. 如果 read 的 wrapper 写成 xor eax,eax; mov al,3，我们的利用会受影响吗？为什么？
  3. 如果程序开了 seccomp，只允许 read / write / open，ORW 链要怎么调整？如果连 open 也被禁，只剩 openat，又该怎么改？

下一步可以试试：带泄漏的 ret2libc、SROP（sigreturn）、seccomp-tools 看沙箱规则，或者把这题换成 64 位版本，用 syscall 重写一遍。
